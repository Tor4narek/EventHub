# EventHub

EventHub помогает студентам вовремя находить мероприятия по интересам. Бот MAX
проводит онбординг, показывает персональную подборку и напоминает о сохранённых
событиях. Мини-приложение даёт каталог с поиском и фильтрами; отдельная админка
предназначена для публикации мероприятий, управления тегами и импорта.

## Доступ к работающему решению

- Бот: [Хакатон МАХ 565](https://max.ru/t565_hakaton_max_bot)
  (`t565_hakaton_max_bot`). Мини-приложение открывается кнопкой «Все мероприятия»
  в меню бота.
- API: <https://api.eventhub.faberlab.tech>.
- Админка: <https://admin.eventhub.faberlab.tech>.
- Мини-приложение: <https://eventhub.faberlab.tech>. Для проверки авторизации и
  сохранений открывайте его из MAX: приложение использует подписанные `initData`.
- Исходный код: <https://github.com/Tor4narek/EventHub.git>.

## Основной пользовательский сценарий

1. Студент открывает бота, нажимает «Начать» и выбирает хотя бы один интерес.
2. Бот сохраняет интересы и показывает до трёх подходящих мероприятий на
   ближайшие семь дней. Подборку можно запросить снова из меню.
3. Студент открывает «Все мероприятия», ищет события и применяет фильтры по
   датам, тегам и формату. В карточке видит дату, место, срок регистрации и
   ссылку на первоисточник.
4. Студент сохраняет мероприятие в боте или мини-приложении. Оно появляется в
   общем списке «Сохранённые», а бот напоминает о событии перед началом.
5. В настройках можно включить или отключить еженедельную подборку; интересы
   можно изменить. Регистрация проходит на сайте организатора.

## Состав и архитектура

| Компонент | Расположение | Назначение |
| --- | --- | --- |
| API, бот, планировщик | `EventHubAPI/EventHubAPI`, `EventHubAPI/MaxBotCore`, `EventHubAPI/Scheduler` | HTTP API, обновления MAX, подборки и уведомления |
| Логика и данные | `EventHubAPI/Services`, `EventHubAPI/Storage`, `EventHubAPI/EventImport` | События, теги, пользователи, EF Core, импорт ITMO Events |
| Изображения | `EventHubAPI/ImageStorage`, MinIO | Загрузка изображений и выдача ссылок через API |
| Админка | `EventHubAdmin` | Ручное создание и проверка мероприятий, управление тегами |
| Мини-приложение | `EventHubFrontend` | Каталог, фильтры и сохранённые мероприятия |
| Инфраструктура | `compose.yaml`, `deploy` | PostgreSQL, MinIO, Nginx и Caddy |

Бот, обработчик его обновлений и планировщик работают в одном процессе API.
Оба фронтенда обращаются к нему через относительный путь `/api`, который
проксирует их Nginx. API хранит данные в PostgreSQL, изображения — в MinIO.
В production Caddy принимает HTTPS для трёх доменов. Текущая конфигурация
рассчитана на один экземпляр API с планировщиком.

## Зависимости и запуск локально

Нужны Docker Engine, плагин Docker Compose, доступ к реестрам базовых образов
и свободные порты из таблицы ниже. На хост не требуется устанавливать .NET,
Node.js или PostgreSQL: сборка компонентов выполняется в Docker. Версии
библиотек указаны в `*.csproj` и `package-lock.json` обоих фронтендов.

1. В корне репозитория скопируйте `.env.example` в `.env` и заполните параметры
   из следующего раздела. Не добавляйте `.env` в Git.
2. Из корня репозитория соберите и запустите все локальные компоненты **одной
   командой**:

   ```bash
   docker compose up --build -d
   ```

3. Проверьте `docker compose ps`. API применяет существующие миграции EF Core
   при запуске. Админка доступна на `http://localhost:8457`, каталог — на
   `http://localhost:5174`, проверка API — на
   `http://localhost:8456/api/max/health`.

### Переменные окружения

Корневой `.env.example` содержит образец всех параметров; пустые значения
нужно заполнить до запуска соответствующих функций.

| Переменные | Назначение и условия |
| --- | --- |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT`, `POSTGRES_HOST` | База данных; пароль обязателен. В контейнере API Compose задаёт адрес `postgres:5432`. |
| `JWT__ISSUER`, `JWT__AUDIENCE`, `JWT__SIGNINGKEY` | Выпуск JWT; ключ подписи должен содержать не менее 32 байт. |
| `ADMIN__USERNAME`, `ADMIN__PASSWORDHASH` | Учётная запись администратора. Хеш можно создать командой `dotnet run --project EventHubAPI/EventHubAPI -- --hash-admin-password` при наличии .NET 10 SDK на хосте. |
| `MAX__BOTTOKEN`, `MAX__APIBASEURL`, `MAX__WEBHOOKSECRET`, `MAX__WEBAPPNAME` | Токен и API MAX, секрет webhook и имя подключённого к боту мини-приложения. |
| `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | Учётные данные сервера MinIO. |
| `MINIO__ACCESSKEY`, `MINIO__SECRETKEY`, `MINIO__BUCKETNAME`, `MINIO__ENDPOINT`, `MINIO__USESSL`, `MINIO__PUBLICBASEURL` | Клиент хранилища и ссылки. AccessKey/SecretKey должны совпадать с данными MinIO. В контейнере API endpoint заменяется на `minio:9000`; для публичного сервера PublicBaseUrl должен указывать на HTTPS API. |
| `API_PORT`, `ADMIN_PORT`, `WEBAPP_PORT`, `MINIO_API_PORT`, `MINIO_CONSOLE_PORT` | Опубликованные порты. |
| `API_DOMAIN`, `ADMIN_DOMAIN`, `WEBAPP_DOMAIN` | Домены профиля `production` для HTTPS; локальный запуск без Caddy их не использует. |
| `SWAGGER__ENABLED` | Включает Swagger UI и маршрут OpenAPI на запущенном API. |
| `CORS__ORIGINS__0` | Необязательный разрешённый origin при прямом обращении браузера к API; при штатном проксировании `/api` фронтендами не нужен. |

В `.env.example` регистр букв может отличаться: конфигурация .NET использует
двойное подчёркивание как разделитель секций.

| Адрес по умолчанию | Компонент |
| --- | --- |
| `127.0.0.1:8456` | API |
| `127.0.0.1:8457` | Админка |
| `127.0.0.1:5174` | Мини-приложение вне MAX: публичный каталог |
| `127.0.0.1:5432` | PostgreSQL |
| `127.0.0.1:9500`, `127.0.0.1:9501` | MinIO API и консоль |
| `80`, `443` | Caddy только в профиле `production` |

Порты меняются через `.env`; при обычном запуске порты приложения и хранилищ
привязаны к localhost.

## Внешние сервисы и работа с данными

Для основного сценария нужен **MAX**: действующий токен бота, доступ API к
`platform-api2.max.ru`, HTTPS webhook `https://<API_DOMAIN>/api/max/webhook`
с секретом из `MAX__WEBHOOKSECRET` и подключённое мини-приложение. MAX нельзя
воспроизвести внутри Docker. Без этих условий локально работают API, админка
и публичный каталог; сообщения бота, подписанные `initData` и сохранения в MAX
требуют настроенного бота. Порядок настройки — в `deploy/README.md`.

Импорт по ссылке поддерживает публичные страницы **ITMO Events**. Полученные
описание, даты и теги проверяет администратор перед публикацией. Мероприятия
других источников, в том числе ВШЭ и СПбГУ, добавляются вручную. Автоматическая
классификация моделью в MVP не применяется.

PostgreSQL хранит пользователей, интересы, мероприятия, теги, сохранения и
состояние уведомлений. MinIO хранит изображения. Даты событий в БД записаны
в UTC, интерфейсы показывают московское время. Публичный каталог и рекомендации
показывают опубликованные будущие события. Снятие с публикации переводит
событие в черновик. Список сохранений общий для бота и мини-приложения.
Администратор может безвозвратно удалить черновик; связанные теги, сохранения
пользователей и записи импорта удаляются вместе с ним. Ранее загруженное
изображение при этом остаётся в MinIO.
Операционные данные находятся в именованных томах Docker и не входят в Git.

### Подготовка тестовых данных

В чистой базе **нет готовых мероприятий**. Для воспроизводимой проверки:

1. Войдите в админку с отдельными тестовыми данными администратора и создайте
   хотя бы один тег, например «IT и программирование».
2. Создайте мероприятие с названием, описанием, местом и ссылкой на источник.
   Назначьте созданный тег; дату начала поставьте на ближайшие семь дней,
   а срок регистрации — в будущем либо оставьте пустым.
3. Опубликуйте мероприятие. Оно должно появиться в публичном каталоге.
4. Для персональных методов используйте **отдельного тестового пользователя
   MAX**, выберите у него тот же интерес и откройте мини-приложение из бота.
   Учётные данные и действительные `initData` не входят в репозиторий.

Для проверок в `DATA-API.yaml` это мероприятие должно оставаться будущим,
дедлайн не должен истечь, а у тестового пользователя оно ещё не должно быть
сохранено до начала проверки.

## Пошаговая проверка и ожидаемое поведение

1. Откройте `/api/max/health`: ожидается `200` и JSON со статусом `ok`.
2. Создайте тег и будущее мероприятие в админке, затем опубликуйте его:
   в «Все мероприятия» появится карточка с названием и датой. Черновик в
   публичном списке не появляется.
3. Откройте бота по ссылке выше, нажмите «Начать» и выберите тег: бот сохранит
   интерес и предложит до трёх мероприятий на ближайшие семь дней.
4. Нажмите «Все мероприятия» в меню бота: откроется мини-приложение MAX.
   Поиск и фильтры изменяют список; карточка показывает первоисточник и
   срок регистрации, если он задан.
5. Сохраните мероприятие в боте или мини-приложении: оно появится в обоих
   разделах «Сохранённые». Повторное сохранение не создаёт дубль.
6. Снимите мероприятие с публикации в админке: оно перестанет показываться
   в публичном каталоге и рекомендациях.

Уведомление отправляется планировщиком перед началом события, поэтому его
проверка требует ожидающего мероприятия и работающего экземпляра API. Для
быстрой проверки можно отдельно проверить сохранение и общий список.

## Контракт API

`openapi.json` содержит полный контракт OpenAPI 3.1; `DATA-API.yaml` описывает
основные проверки API по схеме DATA-API 1.0. Экспорт текущего контракта
выполняется командой `python deploy/export-openapi.py` (нужны Python 3 и
.NET 10 SDK; база данных для экспорта не нужна). Публичный HTTPS-адрес указан
в `DATA-API.yaml`. Доступ администратора предоставляется отдельно, если
проверяется сценарий наполнения каталога.

## Известные ограничения

- Импорт по ссылке реализован для ITMO Events; другие источники вводятся
  вручную. Изменение разметки внешнего сайта может потребовать обновления
  парсера.
- Описание, теги и условия участия импортированного события проверяет
  администратор; модель автоматической классификации не используется.
- В чистой базе нет событий, а MAX, webhook и подписанные `initData` нельзя
  получить только запуском контейнеров.
- EventHub не регистрирует участников: кнопка ведёт на сайт организатора.
  Если организатор изменит условия после публикации, данные нужно обновить
  в админке.

## Остановка и повторный запуск

Из корня репозитория выполните `docker compose down` для остановки и
`docker compose up -d` для повторного запуска. Данные PostgreSQL и MinIO
сохраняются в именованных томах. `docker compose down -v` удаляет эти тома и
**все сохранённые данные**. Production-профиль, DNS, сертификаты и автодеплой
описаны в `deploy/README.md`.

Проверка backend: `dotnet test EventHubAPI/EventHubAPI.sln`. Сборка фронтендов
вне Docker: `npm ci && npm run build` в `EventHubAdmin` и `EventHubFrontend`.
